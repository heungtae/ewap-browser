## Source and trust boundary

- [Node adapter](../../apps/agent-server/src/settings/linux-secret-store.ts) implements SecretStore without a default-store change. The factory checks Linux/profile/helper ownership/permissions/path and probes an unlocked persistent OS collection before returning `mode: os-store`. Each operation launches a bounded Python helper with request/result pipes, fixed interpreter/isolated Python mode, allowlisted D-Bus/XDG/locale environment, hashed identity/profile attributes and masked errors. Values/request/output are bounded; NULs are rejected. No session/plaintext fallback exists.
- [Helper](../../native-host/secret-service.py) uses system libsecret via GI, requires an existing service and default collection distinct from the session collection, and refuses locked/ambiguous items. Its Service subclass refuses synchronous prompting; it does not invoke unlock or collection creation. Item storage/retrieval uses the actual OS API, not an encrypted-file substitute implemented in this repository. Provider URLs/IDs, API keys and header values are not item labels/attributes or argv values.
- Explicit backend injection works with the actual [MG01 service](../../apps/agent-server/src/migration/mg01-settings.ts). The controlled integration fixture accepts an explicit SecretStore override; default fixture callers and normal application composition keep SessionSecrets. No migration RPC for raw secrets or operator consent was introduced.

The helper directory, OS session and Secret Service are trusted. Same-user malicious process protection, memory zeroization and hardware-backed encryption are not claimed. Profiles/hashed identities prevent accidental namespace reuse, not OS-user ACL bypass. Normal native capabilities still report session-only because this adapter is not selected there. [Operations and retention](../migration-os-secrets.md) describe requirements and exclusions.

## Actual isolated verification

The test runner creates a fresh D-Bus session and private temporary XDG data/runtime/control directories, refuses a preexisting Secret Service owner on that bus, installs a protected helper copy and starts its own foreground GNOME daemon. It never overrides HOME or uses the desktop user's collection. Fixture passwords and credential values are passed only through pipes. The final run reports **4/4 PASS**:

1. Write through one helper, read through a fresh helper/store instance; reject other identity/profile reads; stop the actual keyring daemon and fail reads; start locked and fail factory probe; explicitly restart-unlock with the fixture password and read the same persisted value. No plaintext canary appears in persisted keyring files. This observation is not a cryptographic audit.
2. Lock the actual OS collection; read, write and new factory connection fail closed with generic errors and no fallback. After external fixture restart-unlock, the original value remains unchanged.
3. Run all-six controlled migration staging with the actual MG01 SQLite journal and OS store. Restart the backend DB/browser fixture handles and the actual keyring daemon, construct a new OS client and resume/read back. Locking the collection blocks coordinator acknowledgment with qualification namespace still legacy and admission zero. External unlock permits agreement and qualification commit; MG01 SQLite stores `os-store` metadata but neither source API-key nor header canaries. Other source/freeze owners remain controlled fixtures; this is not installed all-six runtime qualification.
4. Reject invalid profile, oversized/NUL values and empty identity before successful OS operations.

Every OS operation uses a fresh helper process. The private daemon is really restarted against its persisted files. Test unlock deliberately restarts the daemon with the fixture password; unlocking an existing live desktop service is not tested or performed by the adapter. OS entries are removed only by deleting the disposable test keyring after teardown; production SecretStore has no automatic delete/purge operation.

## Initial failures and corrections

The initial probe rejected a group-writable development-checkout helper before OS access. Tests now install an owner-private copy instead of weakening the helper check. A subsequent lifecycle test expected the command-line unlock client to unlock an already-running test daemon; the collection stayed locked, and the adapter correctly returned `OS_SECRET_UNAVAILABLE`. The failed fixture also left three owned test daemons alive, causing the remaining fixture setups to fail. Those specific test processes/directories were cleaned up; no normal-user service was stopped.

The corrected fixture rejects preexisting bus owners, cleans construction failures, and uses explicit private-daemon restart-unlock. The runner now controls a detached test process group with a bounded kill deadline so abandoned descendants cannot hold evidence pipes open indefinitely. The original failure is retained here; final TAP/report come from the corrected four-test run. No product auto-unlock, prompting, plaintext fallback or assertion weakening was added.
