# 워크플로우 3개 출처 통합 및 LLM 적합성 검토 방향

상태: Proposed. 2026-10-04. 제품 실행 로직 변경 전 설계 문서다.
사용자 요청: 후보의 의미·대상·실행 범위를 코드가 먼저 확정하거나 좁히지 않는다.
워크플로우 출처는 1·2·3으로 정리한다. 기존 4번 페이지 제공 선언은 3번의
분석 자료로 통합한다. 모든 출처를 현재 페이지 + 코드 + 사용자 요청으로 LLM 검토한다.
WebMCP 구현과 실험 예제는 이번 범위에서 제외하고 향후 표준 확정 뒤 재검토한다.

## 문제와 결정

Search query 입력 요청에서도 페이지의 Preview 선언이 발견되면 후보 선택 화면이
열렸다. Preview를 선택하면 scope 단계의 도구만 제공하면서 원래 입력 요청을
유지해 의미가 충돌한다. 기존 테스트는 '일반 한 단계 실행'을 자동 선택하여 이 경로를
검증하지 않았다. VERIFIED는 도구 없는 답변 완료에도 사용되어 입력 성공과 혼동됐다.

다음 흐름으로 변경한다.

`후보 발견 → 현재 페이지·코드·요청을 함께 LLM 검토 → 근거와 결과 표시 → 사용자 선택 → 최신 상태로 LLM 재검토 → 계획 승인 → 실행 → 실제 결과 검증`

1. 코드가 출처·이름·키워드·요청 종류로 관련 후보를 미리 삭제하지 않는다.
2. origin/fingerprint 불일치도 후보의 상태와 근거로 LLM에 전달한다. 이를 무시하고
   다른 origin에서 기존 실행 권한을 재사용하는 것은 허용하지 않는다.
3. 페이지 선언, 저장 여부, Profile 서명, 후보의 기존 verified 상태는 출처/무결성
   근거다. 현재 사용자 요청에 적합하다는 판정으로 승격하지 않는다.
4. LLM이 적합 후보와 필요한 단계·대상·매개변수 및 관련 없는 부작용을 판단한다.
   일반 한 단계 실행도 LLM이 선택할 수 있는 실행 대안으로 함께 제시한다.
5. 맞지 않는 후보를 사용자가 선택해도 바로 해당 첫 단계로 들어가지 않는다.
   LLM 재검토로 요청과의 불일치를 설명하고 요청 변경/새 계획/추가 질문을 제안한다.
6. 'Search query 입력'을 'Preview 생성'으로 묵시적으로 바꾸거나, 임의로 scope
   옵션을 골라 워크플로우를 진행하지 않는다.

## 후보 출처

| 출처                                      | 검토 입력                                           | 처리 방향                                                                      |
| ----------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------ |
| 1. 내가 저장한 워크플로우                 | 원본 단계·작성 당시 context·현재 UI·현재 코드·요청  | 현재 적합성 검토. 오래된 대상/순서도 증거를 보여 주고 재계획 여부를 LLM이 판단 |
| 2. 서버 Page Profile 워크플로우           | 원본 Profile와 workflow·버전/서명·현재 UI·코드·요청 | 조직 검증과 요청 적합성을 분리. 변경 제안은 원본과 별개의 초안                 |
| 3. 현재 페이지 기반으로 생성한 워크플로우 | 현재 UI·코드·페이지의 설명/선언·요청·가용 실행 도구 | LLM이 요청에 맞는 실행 계획을 생성하고 검토. 페이지의 선언도 근거로만 사용     |

기존 4번은 독립 실행 후보로 등록하지 않고 3번의 입력 자료로 통합한다.
일반 HTML·ARIA·페이지 코드·설명·발견된 선언을 함께 LLM에 전달한다.
ContextPilot 전용 MIME 선언의 존재를 전제로 하지 않는다. 발견된 절차가 있더라도
그 단계와 범위를 실행 계획으로 그대로 확정하지 않는다. LLM이 사용자 요청과의
관련성, 실제 구현과의 일치, 필요한 단계·입력·부작용을 검토해 계획을 생성한다.

UI 후보의 제공 출처는 위 세 가지로 정리하되, 생성 근거가 코드 추론인지 페이지
설명/선언인지 진단 provenance에는 보존한다. 출처의 통합은 근거 정보 삭제나
코드의 의미 필터링을 뜻하지 않는다.

Page Profile을 MCP server에서 얻는 경우도 같은 2번이다. 현재 Browser resolver로
받는 Profile와 향후 MCP resource 경로를 혼동하지 않는다. 공급 경로 자체가
현재 요청에 대한 의미 적합성을 보증하지 않는다.

## LLM 검토의 입력과 출력

입력은 원래 요청 원문, request/tab/document binding, UI snapshot, 마스킹된 코드,
후보 전체 원본, 출처/버전/비교 결과, 실행 가능한 도구의 schema, 기존 승인 범위다.
발견·선택·실행 직전의 검토가 같은 요청과 후보 revision에 묶인다.
현재 활성 워크플로우 단계로 도구를 줄이기 **전에** 적합성·실행 대안을 검토한다.

관련성을 판단하려고 코드 내용까지 필요한 검토에 제목과 UI만 제공하고 완료로
기록하지 않는다. 기존 페이지 코드 전달 동의와 민감값 마스킹은 유지한다.
분량 제한이 있으면 후보/코드를 나누어 검토하고 누락 목록과 근거 범위를 표시한다.
전체를 보지 못하면 추가 context나 clarification을 요청한다. 조용히 후보를 제거하지 않는다.

출력의 설계 예: candidate별 match / partial / mismatch / needs_context 판정,
페이지·코드·요청의 근거, 현재 실행 가능성, 부족한 입력, 원본과 계획의 차이,
불필요한 부작용, 실행 대안, 사용자에게 물을 질문. 이는 신규 확정 계약이 아니다.
confidence 점수나 출처 priority로 코드가 다시 후보를 삭제하지 않는다.
의미 판정과 선택 근거는 LLM 응답을 사용하며 UI는 검토 결과와 다른 후보를 함께 보여 준다.

LLM 검토는 실행 권한 부여가 아니다. schema 검증, 기존 권한, 사용자 승인,
출처 결속, 최신 페이지 확인은 실행의 기술적 경계로 유지한다. 실행할 수 없는
수단은 capability 상태로 설명하며 다른 수단/질문은 LLM이 제안한다. 임의 JS나
미승인 네트워크 호출을 새 실행 권한으로 바꾸지 않는다.

## 웹 형식 도입의 보류

WebMCP를 포함한 웹 도구 제공 형식의 조사 자료는 향후 검토 대상으로 남긴다.
현재 제품·예제·완료 기준에는 WebMCP bridge, tool 등록/호출 또는 native API를
추가하지 않는다. 앞서 만든 `webmcp-preview.html` 실험 페이지도 제거한다.

참고: [WebMCP 초안](https://webmachinelearning.github.io/webmcp/)과
[Chrome 안내](https://developer.chrome.com/docs/ai/webmcp).
향후 확정된 표준과 실제 브라우저 지원을 확인한 뒤 별도 계획으로 추가한다.
이번 구현의 3번은 특정 웹 표준의 존재에 의존하지 않는다.

## 기존 examples 변경 계획

`examples/`에서 실행되는 contextpilot-workflow 선언은
`accessible-items-demo/index.html:324`의 한 블록이다. request 문서, Chrome 결과
문서와 테스트 안내에는 이 선언을 사용하는 요청/기록이 있다.

일반 UI 예제에서 해당 선언을 제거하고 실제 UI event handler는 유지한다.
Preview 절차는 1·2·3 경로의 LLM 검토로 테스트한다. 일반 HTML의 UI·event
handler·화면 설명을 근거로 요청에 맞는 계획을 만들 수 있어야 한다.
기존 독자 형식은 필요 시 명시적인 legacy 호환 fixture로 분리한다.
최신 웹 형식인 것처럼 일반 example에 남기지 않는다. 이번 단계에서는 기존 선언을
삭제하지 않고 전환 계획을 먼저 확정한다. 기존 선언의 제거와 관련 테스트 이전은
LLM 검토 흐름 구현과 함께 진행한다.

기존 테스트의 1.8 요청과 Provider fixture는 page-declared 후보를 가정하므로
선언만 삭제하면 깨진다. 요청 문서, canonical inventory, workflow 선택/승인
자동화, 기존 결과 문서와 16번 설명 문서를 함께 전환한다.
과거 36/36은 지정 경로·통제 Provider 결과이며 새로운 적합성 검토의 증거가 아니다.

## 구현 순서와 완료 기준

1. 검토 context/결과, 출처 표시, 원본과 새 계획의 구분을 Browser 내부 계약으로 설계.
2. 후보 발견 뒤 및 선택/시작 직전에 request-bound LLM 검토를 연결.
3. 의미 적합성 확인 전에 workflow 한 단계로 도구를 좁히는 경로를 전환.
4. 원래 요청을 포함한 코드 분석 초안 생성과 실행 결과 판정을 연결.
5. 기존 page-declared 직접 후보 경로를 3번의 LLM 분석 자료로 전환. 출처·원본
   근거를 보존하고 페이지가 작성한 순서를 곧바로 실행 범위로 사용하지 않음.
6. 일반 UI example 선언 제거, 요청/테스트 이전, 실제 Chrome 증거 갱신.

회귀 검증은 출처 1·2·3 각각 적합/무관/부분 적합/추가 정보 필요, 페이지 변경,
중복 후보, 코드의 설명과 실제 효과 불일치, 후보 설명의 지시문 혼입을 포함한다.
Search 입력 요청에서 Preview 후보가 발견돼도 텍스트 입력 계획을 LLM이 선택하는지,
사용자가 무관한 후보를 선택했을 때도 입력 목표를 묵시적으로 변경하지 않는지 검사한다.
Provider mock은 테스트 case ID로 원하는 도구를 강제하지 않고 전달받은 근거와
검토 응답/선택 경로를 검증한다. 별도 live Provider 검증은 모델/프롬프트/코드 revision을 기록한다.

도구 없는 설명은 ANSWER_ONLY로 표시하고 페이지 조작 VERIFIED와 분리한다.
검토 로그에는 원래 요청, 후보별 근거/판정, 계획 변경, 제공 도구, 실제 호출,
사후 상태와 masking 정보를 request ID로 묶어 기록한다.

## 저장소 경계 및 호환성

workspace의 `specs/workflow.schema.json`, `specs/page-profile.schema.json`, Browser의
workflow catalog/선택/실행 코드, Platform의 resource/Workflow 문서를 확인했다.
공유 ewap/v1의 Workflow와 Browser의 WorkflowDeclaration v1은 동일 계약으로
가정하지 않는다. WebMCP tool descriptor를 이들 계약으로 직접 치환하지 않는다.

이번 산출물은 Browser-local 설계 문서이며 공유 schema·서명·저장 format은
변경하지 않았다. 실제 구현에서 신규 저장 필드/step 종류 또는 외부 review 계약이
필요하면 workspace contract-first와 양쪽 producer/consumer 호환성 검증을 적용한다.
Platform/교차 저장소 통합 테스트는 이번 설계 단계에서 실행하지 않았다.

## 이번 단계의 변경과 검증

설계 문서의 출처·분석 입력·구현 순서·회귀 기준을 세 종류로 갱신했다.
앞서 추가한 WebMCP 실험 HTML은 제거했다. 기존 examples의 선언과 제품 코드,
공유 계약은 아직 변경하지 않았다. LLM 적합성 검토와 기존 36개 테스트 전환은
구현 전이며, 이번 문서 변경에서 컴파일/Chrome 테스트는 재실행하지 않았다.
